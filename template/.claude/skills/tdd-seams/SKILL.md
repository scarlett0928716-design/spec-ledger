# tdd-seams：接缝上的红绿循环

借鉴 mattpocock/skills 的 `tdd`，加上 spec-ledger 的"人确认接缝"闸门（governance R8）。

## 接缝是什么

不进入内部就能观察行为的公共边界。按层级从高到低：

| 层级 | 例子 | 何时选它 |
|---|---|---|
| 对外接口 | HTTP 路由、CLI 命令、导出文件 | 默认首选——行为在这里对用户可见 |
| 公共函数 / 服务 | 模块的 `__all__`、service 层方法 | 接口层覆盖不到的分支 |
| 数据契约 | 表结构、对外事件、消息格式 | 下游依赖这些时 |

**不是接缝**：私有函数、内部状态、某个 ORM 调用是否发生。

## 循环

1. **列接缝**：写测试前先列出候选接缝 + 每条能验证哪些 AC / 行为面，等人确认。未确认的不写。
2. **红**：在一个接缝上写一个测试，跑，确认红（特征测试例外：锁现状必须直接绿）。
3. **绿**：写刚好让它绿的最小实现，不预支功能。
4. **下一条**：回到 2。重构不在红绿循环里，留到 `/refactor` 或 PR 前。

## 三个反模式（见到就停）

| 反模式 | 症状 | 后果 |
|---|---|---|
| 耦合实现 | mock 内部函数、断言私有方法被调用、查数据库代替查接口返回 | 一重构就红，测试变成实现的复印件 |
| 同义反复 | 期望值用被测代码或同一套逻辑算出来 | 永远绿，什么也没验证 |
| 横切 | 先写完所有测试再写所有实现 | 失去"每一步都有反馈"的意义 |

期望值来源只能是：spec 里的字面值、独立手算的算例、或特征测试里"实际跑一次得到的值"（并注明）。

## 命名

测试名用 CONTEXT.md 的术语；特征测试以 `_currently` 结尾，回归测试以 AC 编号开头或在注释里引用 AC。
