# 02 · Spec 生成（从需求到规格，含自检）

## 使用场景

拿到一个需求 / issue，需要先写 spec 再实现。生成后 AI 必须对 spec 做一轮自检（含糊点 / 矛盾 / 不可测 / 领域假设），再交人审。

## Prompt 模板

```
请基于以下需求，用 spec/SPEC_TEMPLATE.md 的格式生成一份 spec 草案，
写到 spec/planned/<id>-<简短名称>.md（id 沿用本项目前缀和下一个序号）。

需求描述：
[粘贴 issue 内容或口头需求]

相关上下文：
[粘贴相关代码路径、现有 spec、docs/survey/ 下的梳理结果、依赖关系等]

第一步：生成 spec
1. 明确"边界（什么锁死）"——哪些接口、返回结构、兼容约束不能变
2. 明确"实现空间"——哪些细节留给实现者发挥
3. 明确"不做什么"——显式排除的范围
4. 验收标准编号 AC-1、AC-2……每条必须可测试——能直接转成一个测试断言
5. 如果涉及遗留代码，填写"行为面清单"
6. 如果能分步，给出实现步骤建议

第二步：自检（写进 spec 第 9 节"自检记录"）
逐条检查并列出：
- 含糊点：哪些词没有量化（"及时""大量""合理"）、哪些场景没说清
- 内部矛盾：边界 vs 验收标准 vs 不做什么 之间有没有打架
- 不可测条目：哪条验收标准写不成断言，改写成可测的版本
- 领域假设：你为了把 spec 写完整而默认了哪些业务语义（概念等同、主键、主路径）
每条标注：已自行澄清 / 待人裁决。不要把"待人裁决"的项当成已决定。

第三步：输出
- spec 文件路径
- 自检摘要：待人裁决的条目列表（这是人审的入口）

这是草案，人审批后才会进入 /tasks 和实现。
```

## 人审要点

- [ ] 边界是否画得够紧（防止 AI 自由发挥过头）？
- [ ] 验收标准是否够具体（能直接写测试）？
- [ ] "不做什么"有没有遗漏（AI 最爱做的"顺手优化"）？
- [ ] 自检记录里"待人裁决"的每一条，都裁决了吗？
- [ ] 领域假设是否符合实际业务（这一项只有人能判断）？
- [ ] 有没有忽略兼容约束？
