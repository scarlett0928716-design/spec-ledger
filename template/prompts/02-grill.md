# 02 · 追问（Grill：写 spec 之前，让 AI 把你问到没有含糊）

## 使用场景

需求已分流为新功能 / API 变更 / 架构变更，但还没写 spec。
与其让 AI 自己猜边界再"自检"，不如让 AI 先把问题抛给你——**你只负责裁决，不负责想问题**。
借鉴自 mattpocock/skills 的 `grilling`。

## 前置条件

- `/triage` 已给出类型判断
- 涉及遗留代码的，`/survey` 已完成（AI 要先懂现状才问得出好问题）

## Prompt 模板

```
请对以下需求做一轮追问（grill），目的是在写 spec 之前消除所有含糊。

需求：
[粘贴 issue / 口头需求]

已知上下文：
[docs/survey/ 梳理结果、相关 spec、CONTEXT.md 词汇表]

追问规则：
1. 一次只问一个问题，等我回答再问下一个；不要一口气列十个
2. 从影响最大的问题开始：先问"边界"（什么不能变）、再问"验收"（怎么算做完）、最后问"排除"（明确不做什么）
3. 每个问题附上你当前的默认假设——我不回答时你会按什么做
4. 遇到领域术语（两个概念是不是一回事、哪个是主路径、哪个字段是主键）：先查 CONTEXT.md；
   表里没有的，把它作为问题提出，并在我裁决后记入 CONTEXT.md 的"待确认"区
5. 不要问能从代码或文档里自己查到的问题——先查，查不到再问
6. 我说"够了"或连续两个问题你都已经能从前面的回答推出答案时，停止追问

结束时输出"裁决记录"：
| # | 问题 | 裁决 | 进入 spec 哪一节 |
这份记录直接作为 /spec 的输入；新术语同步写入 CONTEXT.md。

不要开始写 spec，不要写代码。
```

## 人审要点

- [ ] 它问的是"你才知道"的事，还是它自己能查到的事？后者说明它偷懒了
- [ ] 默认假设有没有让你不舒服的——那就是必须裁决的地方
- [ ] 裁决记录里每条是否能对应到 spec 的某一节（3.1 边界 / 4 验收 / 3.3 不做什么）
- [ ] 新术语是否真的进了 CONTEXT.md

## 与 /spec 自检的关系

两者互补：**grill 在前**，把人才知道的事问出来；**自检在后**，把 AI 自己写出来的 spec 再过一遍逻辑一致性。小需求可以跳过 grill 直接 /spec；涉及遗留代码或 public API 的不建议跳。
