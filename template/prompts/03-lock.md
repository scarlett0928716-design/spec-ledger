# 03 · 特征测试（锁住现状）

## 使用场景

架构梳理完成后、重构之前，把当前行为（包括可疑行为）原样锁进测试。

## 前置条件

- 已完成架构梳理（docs/survey/ 或 spec 的行为面清单）
- 已确认可疑行为清单
- 人已审批"哪些行为必须锁住"

## Prompt 模板

```
基于以下架构梳理结果，请生成特征测试。

[粘贴架构梳理输出，或引用 docs/survey/<模块>.md / spec 文件路径]

要求：

1. 测试锁住当前行为，不判断当前行为是否合理
2. 可疑行为必须原样锁住（即使看起来像 bug）
3. 覆盖以下行为面：
   - 返回值/返回结构（字段名、精度、嵌套）
   - 异常/拒绝路径
   - 数据库副作用（写了什么记录）
   - 事件/日志（触发了什么事件、写了什么日志）
   - 全局状态变化
   - public import 路径（如果有）
4. 隔离要求：
   - 数据库用临时库/mock
   - 全局变量每个测试前 reset
   - 测试之间不能有顺序依赖
5. 命名规范：
   - 测试名写"锁现状"而非"应该怎样"
   - 示例：test_vip_and_coupon_stack_currently（而非 test_vip_and_coupon_should_stack）
6. 每条测试附注释说明它锁住了哪条现状行为

不要修改业务代码。
测试放在 tests/characterization/ 目录。
写完后运行质量门禁（bash scripts/gate.sh），必须全绿——红了说明锁的不是现状，改测试不改代码。
```

## 人审要点

- [ ] 测试锁的是"现在怎样"还是"应该怎样"？
- [ ] 可疑行为是否原样锁住（不是修正后的理想行为）？
- [ ] 数据库/全局状态是否正确隔离？
- [ ] 行为面覆盖够不够（参照 SPEC_TEMPLATE 第5节的清单）？
- [ ] 测试命名是否明确表示"锁现状"？

## 铁律

**没有特征测试全绿，不许 AI 重构这块代码。**
