# spec-ledger 操作手册

> 方法论源自莫欣老师 AI Coding 课程（第 16–18 课），在真实的企业系统项目中跑通后整理；适用于 Claude Code、Codex、Cursor 及任何支持 AGENTS.md 的 agent。

---

## 一、整体工作流

```
需求 / issue 进来
    │
    ▼
┌──────────────────┐
│ 0. 分流          │  ← /triage：bug？新功能？API？遗留代码？
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 1. 理解现状      │  ← /survey：AI 只读不改，产出 docs/survey/
└────────┬─────────┘      （仅遗留代码需要）
         ▼
┌──────────────────┐
│ 2. 追问          │  ← /grill：AI 一次一问，人只裁决；新术语进 CONTEXT.md
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 3. 写 Spec + 自检 │  ← /spec：定义边界，列出待裁决项 → 人审批
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 4. 锁住行为      │  ← /lock：列接缝 → 人确认 → 特征测试跑绿（仅遗留代码需要）
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 5. 拆任务账本    │  ← /tasks：commit 粒度，落盘 *.tasks.md
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 6. 实现 / 重构   │  ← /feature 或 /refactor：列接缝 → 小步红绿，实时更新账本
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 7. 提交验证      │  ← /pr：门禁（pre-commit + CI）+ PR + 人审
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 8. 同步账本      │  ← 人：spec 移到 implemented，填锚点，账本随行；词汇表待确认项清零
└──────────────────┘
```

## 二、场景分流

### 场景 A：新功能开发

1. `/triage` 确认是 B 类（新功能）
2. `/grill`：AI 一次一问，你只答"对 / 不对 / 改成…"；新术语进 CONTEXT.md 待确认区
3. `/spec` 生成 planned spec + 自检记录（以裁决记录为输入）
4. 人审：边界、验收标准、不做什么、**逐条裁决自检记录里的待裁决项**；把词汇表待确认项移入正式表
5. `/tasks` 拆账本
6. `/feature`：先列测试接缝等你确认，再按账本 TDD 实现
7. 门禁全绿 → `/pr` → 人审 → 合并
8. 人把 spec 和账本移到 implemented，填实现锚点

### 场景 B：遗留代码重构

1. `/survey`：AI 只读，产出结构理解到 `docs/survey/`
2. 人审梳理结果（public API、隐式状态有没有漏）
3. `/grill`：针对"哪些行为必须保持、哪套实现是主路径"追问，答案进 CONTEXT.md
4. `/spec`：基于梳理和裁决写"当前行为 + 重构目标"spec，行为面清单必填
5. `/lock`：先列接缝等确认，再生成特征测试锁住当前行为（包括可疑行为）
6. 跑绿：特征测试全绿才算锁住
7. `/tasks` 拆账本（每个重构步骤前置"特征测试全绿"）
8. `/refactor`：一次一个职责块，每步跑测试，每步一个 commit
9. 红灯处理：行为变了就停，判断是回退还是单独修 bug

### 场景 C：修 Bug

1. `/triage` 确认是 A 类（局部 bug，期望清楚）
2. 确认 bug 对应的 spec（没有就先补一个最小 spec）
3. 写回归测试：让测试在 bug 存在时红
4. 修代码让测试绿
5. 确认其他测试没红
6. `/pr`，PR 只包含 bug fix，不混重构

## 三、四个账本

| 账本 | 位置 | 记什么 | 谁能改 |
|---|---|---|---|
| 规则账本 | `AGENTS.md`、`spec/governance/` | 长期不变的纪律 | 只有人 |
| 词汇账本 | `CONTEXT.md` | 术语、主键、主路径、禁用说法 | 正式表只有人；AI 只能追加"待确认" |
| 规格账本 | `spec/planned|implemented|archived/*.md` | 每个功能的边界、验收标准、状态 | 内容 AI 可起草，**状态只有人能动** |
| 任务账本 | `spec/planned/*.tasks.md` | commit 粒度的进度 | AI 可改状态列和 commit 列 |

账本落盘解决的是一个具体问题：AI 对话没有记忆，换会话、换 agent、隔一天回来，所有"做到哪了"都要重讲。账本在仓库里，进度跟着代码走。

## 四、红灯处理决策树

```
测试红了
    │
    ├─ 是特征测试红？
    │       │
    │       ├─ 行为确实变了 → revert 最近一步，缩小重构范围，账本任务 ⏸
    │       │
    │       └─ 测试本身写错了（锁了理想而非现状）→ 人确认后修测试，记录原因
    │
    └─ 是回归测试红？
            │
            ├─ 新代码破坏了已有功能 → 修新代码，不改测试
            │
            └─ 测试过时（spec 已更新但测试没跟）→ 同步测试到新 spec
```

## 五、人的角色清单

AI 做体力活，人做以下事：

| 环节 | 人的动作 |
|---|---|
| 需求进来 | 判断 issue 类型，决定要不要先写 spec |
| 追问（grill） | 回答 AI 的问题，对默认假设说对或不对 |
| 词汇表 | 把 CONTEXT.md 待确认区移入正式表或打回 |
| Spec 审批 | 确认边界对不对、验收标准够不够、不做什么有没有漏；**自检记录里每一条待裁决项都要裁决** |
| 领域假设 | AI 默认的业务语义（概念等同、主键、主路径）只有人能确认 |
| 架构梳理审 | 确认 AI 列出的 public API、隐式状态有没有遗漏 |
| 接缝确认 | AI 列出要在哪些公共边界上测，确认层级对不对 |
| 特征测试审 | 确认锁的是现状还是理想，可疑行为有没有原样锁住 |
| 任务账本审 | 每个任务是否一个 commit 能完成，每条 AC 是否有人认领 |
| 重构审 | 看 diff 是否只做了一件事，行为是否不变 |
| PR 审 | 确认 commit 信息、测试覆盖、账本与 spec 对齐 |
| 按 merge | 最终决策权永远在人 |
| Spec 状态移动 | 只有人可以移动 spec 到 implemented / archived |

## 六、质量飞轮

```
AI 生成（spec 草案 / 账本 / 测试 / 代码）
    → 验证（自检记录 / 门禁 / 特征测试 / PR 模板）
    → 失败信息结构化回喂给 AI
    → AI 修正
    → 人最终裁决
    → 知识沉淀（spec 更新 / 测试补全 / governance 规则新增）
    → 下一轮生成质量更高
```

governance 规则就是从翻车里提炼出来的。每次翻车问一句："哪条规则能让它不再发生？"写进 `spec/governance/`。

## 七、从零开始

### 已有项目接入

1. `bash install.sh <项目目录>`（不覆盖已有文件）
2. 填 `AGENTS.md` 第零节项目参数
3. `bash scripts/setup.sh` 启用门禁并试跑
4. 挑一个最不敢动的老入口 → `/survey` → `/lock` → 全绿
5. 这两步做完，才让 AI 动它

### 新项目从零搭建

1. `bash install.sh <新目录>`，初始化项目结构
2. 第一个功能：`/spec` → 人审 → `/tasks` → `/feature` → `/pr`
3. 每个后续功能重复这个循环
4. 积累 governance 规则（从踩坑中提炼）

## 八、常见翻车与应对

| 翻车场景 | 原因 | 应对 |
|---|---|---|
| AI 重构后行为变了但测试没红 | 特征测试覆盖面不够 | 补测试，扩大行为面清单 |
| AI 在重构 PR 里顺手修了 bug | AI 不区分重构和修 bug | R1 铁律，PR 打回 |
| Spec 和代码不一致 | PR 合并后没同步 spec | PR checklist 强制检查；人移状态时核对锚点 |
| AI 改了 public API | 没把 API 约束写进 spec | 在 spec 的"边界"节显式列出 |
| 特征测试锁了理想行为 | AI 按"应该怎样"而非"现在怎样"写测试 | 审测试时看命名和注释是否写"锁现状" |
| AI 产出太多看不过来 | 步子太大 | 账本粒度改小，一次只给一个任务 |
| 换个会话 AI 又从头来 | 进度只在对话里 | 账本落盘（R7），会话结束前必须更新 |
| AI 自己拍板了业务语义 | 术语没有落盘载体 | CONTEXT.md 词汇表 + `/grill` 先问（R6） |
| 一重构测试就红、测试像实现的复印件 | 测试写在内部实现上 | 接缝纪律（R8）：先列接缝人确认，不 mock 内部 |
| 写 spec 时人想不出边界 | 让人凭空想问题 | `/grill`：AI 提问人裁决，把思考成本转到 AI 侧 |
| 门禁被绕过 | 只靠文字约束 | pre-commit hook + CI 共用 gate.sh |
