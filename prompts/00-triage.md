# 00 · Issue 分流（决定走哪条路）

## 使用场景

一个新需求 / issue 进来，先判断它是哪种类型，再决定要不要写 spec、先锁什么。

## Prompt 模板

```
以下是一个新 issue。请帮我判断它属于哪种类型，以及应该怎么处理。

[粘贴 issue 内容或口头需求]

类型选项：
A. 局部 bug，期望已清楚 → 最小修复 + 回归测试（不需要新 spec）
B. 涉及新功能 → 先写 planned spec（/spec）
C. 涉及 public API 变更 → 先对齐兼容策略，再写 spec
D. 涉及架构边界 → 先画方案，人定后再写 spec
E. 多个 issue 像同一根因 → 先抽象统一方案
F. 分不清影响面 → 先做架构梳理（/survey），再回来分流

输出：
1. 类型判断 + 理由（引用 issue 原文里的依据）
2. 影响面初估：会碰到哪些入口 / 表 / 下游
3. 是否涉及遗留代码（是 → 必须先 /survey → /lock）
4. 建议的下一步（具体到用哪个 prompt / 命令）
5. 你不确定、需要人裁决的问题（尤其是业务语义）

不要开始写代码。
```

## 人审要点

- [ ] 类型判断的依据是不是来自 issue 原文，而不是 AI 的想象？
- [ ] 影响面有没有漏掉隐式依赖（全局变量、import 副作用、定时任务）？
- [ ] "需要人裁决"的问题有没有真的裁决，而不是默认跳过？
