# 05 · 任务拆解（把 spec 拆成落盘的任务账本）

## 使用场景

spec 已人审通过。实现之前，先把它拆成 commit 粒度的任务，写进 `spec/planned/<spec>.tasks.md`。
账本落盘的意义：换会话、换 agent、隔天接手，都从账本继续，不用重新理解、不用重新拆。

## 前置条件

- spec 状态为 planned，且人已审批（自检记录里没有未裁决项）

## Prompt 模板

```
请把 spec/planned/<id>-<name>.md 拆成任务账本，
用 spec/TASKS_TEMPLATE.md 的格式写到 spec/planned/<id>-<name>.tasks.md。

拆解规则：
1. 粒度：一个任务 = 一个 commit 能完成、一次门禁能验证
2. 顺序：按 TDD 红绿节奏排——"为 AC-n 写红测试"和"实现让它变绿"是两个相邻任务
3. 每个任务标注覆盖的验收标准编号（AC-n）；每条 AC 至少被一个任务覆盖
4. 标注任务间依赖；能并行的不要串起来
5. 涉及遗留代码的任务，前置任务必须是"特征测试全绿"（引用 tests/characterization/ 里的文件）
6. 最后一个任务固定为"跑质量门禁 + 整理 commit + 更新账本"
7. 填写"覆盖检查"表，证明没有 AC 被漏掉

输出：
- 账本文件路径
- 任务总数、预计 commit 数
- 你拆解时发现 spec 本身的问题（如果有，回报人，不要自行改 spec）

不要开始实现。
```

## 执行期规则（给实现阶段的 agent）

- 开始一个任务前把状态改为 🔴，测试绿后改 🟢，提交后改 ✅ 并填 commit 哈希
- 遇到阻塞改 ⏸，在"阻塞与裁决记录"写明问题，停下等人
- 会话结束前账本必须是最新状态——这是 R7 账本铁律

## 人审要点

- [ ] 每个任务是不是真的一个 commit 能做完？
- [ ] 覆盖检查表里有没有 AC 没人认领？
- [ ] 遗留代码任务前面有没有"特征测试全绿"这道闸？
